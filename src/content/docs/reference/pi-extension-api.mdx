## Extension File Location

Extensions are placed in `pi.extensions_dir` (or auto-discovered from the `extensions/` directory next to the binary). All `.ts` and `.js` files in the directory are loaded automatically.

## ExtensionFactory

Every extension exports a default factory function:

```typescript
type ExtensionFactory = (pi: PiInstance) => void;
```

```typescript
import type { ExtensionFactory } from "@mariozechner/pi-coding-agent";

const ext: ExtensionFactory = (pi) => {
  // Register hooks and tools here
};

export default ext;
```

## Event Hooks

### `pi.on("tool_call", handler)`

Intercept tool calls before execution.

```typescript
pi.on("tool_call", async (event, ctx) => {
  // Inspect and decide
  return undefined;
  // or
  return { block: true, reason: "Reason for blocking" };
});
```

**Event fields:**

| Field | Type | Description |
|-------|------|-------------|
| `event.toolName` | `string` | Tool name (e.g., `bash`, `edit`, `write`) |
| `event.toolCallId` | `string` | Unique ID for this call |
| `event.input` | `Record<string, any>` | Tool input parameters — cast fields explicitly: `event.input.command as string` |

**Context fields:**

| Field | Type | Description |
|-------|------|-------------|
| `ctx.ui` | `UIContext` | UI methods for HITL dialogs |
| `ctx.hasUI` | `boolean` | `false` in print/JSON mode — check before calling `ctx.ui` methods |

**Return value:**

| Value | Behavior |
|-------|----------|
| `undefined` (or nothing) | Allow tool execution |
| `{ block: true, reason?: string }` | Block execution, optional reason logged |

Handlers must be `async` when using `ctx.ui` methods — the runtime awaits them.

## Tool Registration

### `pi.addTool(definition)`

Register a custom tool the agent can use.

```typescript
pi.addTool({
  name: "my-tool",
  description: "What this tool does",
  parameters: {
    type: "object",
    properties: {
      query: { type: "string", description: "The search query" },
    },
    required: ["query"],
  },
  execute: (input: { query: string }) => {
    return `Result for: ${input.query}`;
  },
});
```

| Field | Type | Description |
|-------|------|-------------|
| `name` | `string` | Tool name (must be unique) |
| `description` | `string` | Description shown to the LLM |
| `parameters` | JSON Schema | Input parameter schema |
| `execute` | `(input) => string` | Tool implementation |

## UI Methods

### `ctx.ui.confirm(title, details)`

Trigger a HITL approval flow.

```typescript
pi.on("tool_call", async (event, ctx) => {
  if (event.toolName === "bash") {
    const command = event.input.command as string;

    if (!ctx.hasUI) {
      // Block by default when no UI is available (print/JSON mode)
      return { block: true, reason: "Command blocked (no UI for confirmation)" };
    }

    const approved = await ctx.ui.confirm(
      "Destructive Operation",
      `Command: ${command}`
    );
    if (!approved) {
      return { block: true, reason: "Denied by user" };
    }
  }
  return undefined;
});
```

**Returns:** `Promise<boolean>` — `true` if approved, `false` if denied or timed out

**Flow:**
1. Sends `extension_ui_request` to AgentLoop bridge
2. Bridge broadcasts `event.hitl_request` to clients
3. Client presents approval UI
4. Client responds via `hitl.respond`
5. Promise resolves with the decision

If the user chooses "abort", the entire session is aborted (not just the tool call).

**Always check `ctx.hasUI` first.** In non-interactive modes (print, JSON), `ctx.ui.confirm()` returns `false` immediately without showing any UI — omitting the guard silently blocks every tool call.

## Environment Variables

Extensions access server-set variables via `process.env`:

```typescript
const paths = process.env.AGENTLOOP_ALLOWED_PATHS || "";
const dockerAllowed = process.env.AGENTLOOP_DOCKER_ALLOWED || "ps,logs,images";
```

**Convention:** Use `AGENTLOOP_*` prefix for all extension configuration.

| Variable | Description | Default |
|----------|-------------|---------|
| `AGENTLOOP_ALLOWED_PATHS` | Comma-separated allowed file paths | (empty = no restriction) |
| `AGENTLOOP_DOCKER_ALLOWED` | Comma-separated allowed docker subcommands | `ps,logs,images,build,compose,inspect,stats` |
| `AGENTLOOP_DOCKER_BLOCKED_VOLS` | Comma-separated blocked volume paths | `/etc,/var,/root,/proc,/sys,/dev` |
| `AGENTLOOP_HITL_FORCE_KEYWORDS` | Bash keywords that trigger forced HITL approval | From `hitl.force_hitl_keywords` in config |
| `AGENTLOOP_INJECTION_PROTECTION` | Enable/disable prompt injection protection | `true` |
| `AGENTLOOP_WHITELIST_SOURCES` | Comma-separated allowed read paths | From `security.injection.whitelist_sources` |
| `AGENTLOOP_BLOCKED_KEYWORDS` | Comma-separated injection trigger keywords | From `security.injection.blocked_keywords` |
| `AGENTLOOP_MAX_CONTENT_LENGTH` | Max content size in bytes | `50000` |

## Existing Extensions

### security-policy.ts

**Type:** Permission gate

**Intercepts:** `bash`, `write`, `edit` tool calls

**Blocks:**
- Dangerous bash patterns: `rm -rf /`, `sudo rm`, `mkfs`, `dd if=`, fork bombs
- Environment exfiltration: `printenv`, `env |`, `echo $ANTHROPIC`, `echo $OPENAI`, `cat /proc/*/environ`
- Write operations outside allowed paths

### docker-guard.ts

**Type:** Permission gate + HITL

**Intercepts:** `bash` tool calls containing `docker` or `docker-compose`

**Validates:**
- Subcommand against `AGENTLOOP_DOCKER_ALLOWED` whitelist — blocked immediately on violation
- Volume mounts (`-v`/`--volume`) against `AGENTLOOP_DOCKER_BLOCKED_VOLS` — blocked immediately on violation
- All commands that pass both checks still require explicit `ctx.ui.confirm()` approval

### force-hitl.ts

**Type:** HITL gate

**Intercepts:** `bash` tool calls

**Behaviour:** Any bash command containing a keyword from `AGENTLOOP_HITL_FORCE_KEYWORDS` pauses for `ctx.ui.confirm()` before executing. Keywords are set in `agentloop.yaml` under `hitl.force_hitl_keywords` and injected by the Go orchestrator.

**Default keywords:** `sudo`, `chmod`, `chown`, `systemctl`, `npm install`, `pip install`, `yarn add`

## Limitations

- Extensions **cannot import from each other** — each is loaded independently by pi
- Extensions run in the **pi subprocess** (Node.js), not the Go server
- Extensions have access to **Node.js built-in modules** (`fs`, `path`, `os`, etc.)
- Extension hooks fire in **registration order**
- If any hook returns `{ action: "block" }`, the tool call is blocked regardless of other hooks
